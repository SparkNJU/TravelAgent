# 旅游规划 Agent 现状文档 (v2.0)

> 版本：ReAct Agent 架构重构版
> 
> 说明：本文档基于当前 agent 目录下的最新代码实现整理，描述升级后的 Agent 架构、流式接口与落地现状。

## 1. Agent 定位

当前旅游规划 Agent 已升级为一个基于大语言模型（LLM）驱动的**智能体服务**，职责包括：
- 提供 Server-Sent Events (SSE) 流式接口与前端/后端进行实时交互
- 接收用户的自然语言旅行规划请求
- 动态自主调用工具（如联网搜索 Serper、天气查询 Weather、文档解析 FileParser）
- 利用 MetaPlanner 进行复杂目标的任务拆解和规划
- 综合上下文和工具返回，生成最终的旅行计划

整体上，它已经从之前的“规则驱动”演变为“LLM 驱动的规划与执行 (Plan-and-Solve / ReAct)”智能体架构。

## 2. 目录结构

当前 gent 目录的核心结构如下：

- main.py ：FastAPI 入口，暴露对外流式接口
- models.py ：请求体模型 AgentChatRequest
- config/ ：配置文件加载模块
- services/
  - llm_service.py ：封装大模型接口的底层调用
  - eact_agent.py ：智能体核心逻辑（Thought, Action, Observation）
  - planner.py ：MetaPlanner 负责初始任务规划和拆解
  - 	ool_registry.py ：统一的工具注册中心
  - serper_client.py 等 ：具体工具的实现
  - sse_events.py ：SSE 数据流的标准化构造辅助函数
- docs/ ：接口与状态文档
- equirements.txt ：运行依赖

## 3. 架构设计现状

### 3.1 分层方式

1. **入口层 (main.py)**
   - 初始化 FastAPI、各个工具类、模型服务、智能体与规划器
   - 拦截 /api/agent/chat 路由，并转化为 SSE 流式响应机制向下透传

2. **核心业务处理层 (eact_agent.py, planner.py)**
   - **MetaPlanner**：在处理非常复杂的需求时，先让 LLM 输出步骤拆解（Plan）
   - **ReActAgent**：根据问题和计划，利用 LLM 进行推理（Thought），动态选择工具（Action），根据工具结果（Observation）进行下一步推理

3. **基础组件层 (llm_service.py, 	ool_registry.py)**
   - **LLMService**：解耦具体厂商的 LLM SDK，提供统一的生文方法
   - **ToolRegistry**：提供通用的工具元数据映射，和动态路由调用能力

4. **外部能力层（各种 Tool）**
   - 封装了 Web 搜索、天气查询、PDF/Word 文件解析等能力

### 3.2 运行方式

- **无状态流式响应**：当前的请求处理采用 SSE 单向流模型。在 LLM 思考、规划、调用工具的过程中，会不断向客户端推送中间状态（如 plan, 	hought, 	ool_call, message）。
- 服务依然是单次请求模型，但在单次请求内具备多步推理与反思修正的能力。

### 3.3 能力边界

- **不再局限于规则**：天数和目的地提取不再依赖简单的正则，全交由 LLM 理解抽象。
- **自动容错与自修复**：如果工具调用失败或参数错误，Agent 可以通过返回的报错信息自行反思并重试（Self-Correction）。

## 4. 主要代码实现现状

### 4.1 main.py
- 初始化依赖：LLMService, 工具集合, ReActAgent。
- 接口 /api/agent/chat 对应一个 generator 函数 event_stream()，它会 yield 多种 SSE 事件格式的字符串，最后发送 [DONE] 标志结束连接。

### 4.2 models.py (AgentChatRequest)
主要字段变更为：
- query: 用户输入的指令
- mode: plan 模式只出计划不执行；gent 模式按照计划深度执行
- generate_plan_first: 布尔值，是否在展开动作前先构建拆解步骤
- 以及用于接收上传文件的 base64 相关字段。

### 4.3 工具与服务 (services/*)
- 设计了一套面向对象的 Prompt 解析与 Function Calling 的平替（或直连）闭环逻辑。

## 5. 对后端暴露的 API

请查阅同目录下的 [pi.md](api.md) 获取最新、最详尽的接口文档及字段解释。包含：

- GET /health 检测服务状态及启用的 Tools。
- POST /api/agent/chat 主对话端点，接收 JSON 返回 SSE。

## 6. 与后端接入关系

后端的接入方式发生了根本变化：
- 后端 / 前端 必须支持接收解析 	ext/event-stream。
- 我们不再返回一次性的结构化大 JSON，而是不断吐露过程日志和数据片段。页面 UI 可以选择性地渲染 Agent 的内部 Thought 作为思考流（提升用户体验）。

## 7. 当前实现的优点
- **智能化与灵活性大幅提高**：不再是写死流程的代码，具备理解变长且模糊需求的弹性。
- **扩展性极强**：添加新能力只需新写一个 Tool 类（定义描述、参数名）塞入 Registry 即可。
- **体验现代化**：通过流式方式暴露大脑思考过程，从根本上缓解等待大模型长尾请求时的无响应期。

## 8. 当前实现的不足
- 未维护跨请求的会话级 Memory 上下文结构，多轮聊天仍需要前端或后端手动在 query 拼接历史。
- Token 成本和延迟增加：ReAct 多轮循环在复杂业务时会产生大量请求交互开销。

## 9. 后续可演进方向
- 引入外置 Vector DB 支持大规模知识库的 RAG（Retrieval-Augmented Generation）。
- 完善全局 Memory（会话和历史），将对单次 query 的理解扩展成对多帧 messages 的交互处理。
